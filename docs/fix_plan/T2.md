# T2 — База продуктов: восстановить микронутриенты и исправить данные

**Файлы (только эти):** `assets/foods.json`, `assets/db/eco_fit.db`,
`tooling/**` (скрипты). Dart-код НЕ трогать.

## Контекст

02.07.2026 база `eco_fit.db` была пересобрана из `assets/foods.json` — и потеряла
почти все микронутриенты. Старая база (в git-истории, коммит `8f5e262`) имела
35 нутриентов с данными: vit_a/b1/b2/b3/b5/b6/b9/b12/c/d/e/k/h, i (йод), se, cu,
mn, cr, co, mo, f, cl, s, zn и т.д. Новая — только 6 минералов (k, na, mg, ca, p,
fe), причём покрытие fe упало с 933 до 388 продуктов. Витаминные коды vit_a/vit_c/
vit_d/zn есть в схеме `nutrients`, но 0 строк в `food_nutrients`.

Причина: в foods.json микронутриентов никогда не было (блок `per_100g.micros`
содержит только 6 минералов), а старая БД была собрана из более богатого источника.

## Задача

1. Достать старую базу: `git show 8f5e262:assets/db/eco_fit.db > /tmp/old.db`
   (в PowerShell: `git cat-file blob 8f5e262:assets/db/eco_fit.db | ...` или
   через Python). Старая схема: `food_nutrients(food_id, nutrient_id, amount_per_100)`
   — проверь имена колонок, они немного отличались от новой (`amount_per_100` vs
   `amount_per_100g`).
2. Выгрузить из старой базы все микронутриенты по slug продукта
   (foods.slug ↔ nutrients.code ↔ amount + default_unit_code).
3. **Исправить известные ошибки данных ПЕРЕД мержем** (подтверждены аудитом
   по старой базе, реальные значения сверь со справочниками USDA/росс. таблицами):
   - `qoy_beli` (баранья корейка): vit_b5 = 650 мг → **0.65 мг** (ошибка ×1000);
   - `uz_creatine`: cr (хром) = 100000 мкг → **удалить запись** (креатин ≠ хром);
   - `laminariya_dengiz_karami`: i (йод) = 200000 мкг → **~300 мкг** (значение
     сухой ламинарии приписано готовому продукту);
   - `dorado`: vit_d = 570 мкг → **~14 мкг** (IU записали как мкг). Продукта
     `dorado` в новой базе нет — проверь, не переименован ли (поищи по
     food_translations LIKE '%дорад%'); если продукт удалён насовсем — пропусти.
   - Просмотри топ-10 максимумов по каждому витамину/минералу из старой базы
     глазами на правдоподобие (единицы mg/mcg!) — там могут быть ещё выбросы
     той же природы.
4. Вмержить микры в `assets/foods.json` (блок `per_100g.micros` по slug — ключи
   кодов как в старой базе: vit_b2, se, i и т.д.). Продукты, которых больше нет
   в новой базе, пропустить; новые продукты без микро-данных оставить как есть.
5. Проверить `tooling/build_offline_db.py`: откуда берётся список кодов таблицы
   `nutrients` — если он захардкожен 16 кодами, расширить, чтобы все коды из
   foods.json попадали в БД (с правильным default_unit_code — сверь со старой
   базой: mcg для vit_a/d/k/b9/b12/h/i/se/cr/mo/co, mg для остальных).
   Dart-сторона читает коды динамически (`_loadMicros`), маппинг единиц — в
   `lib/nutrition/micronutrients.dart` (НЕ менять, просто сверь коды и единицы).
6. Пересобрать: `python tooling/build_offline_db.py` (посмотри как он
   запускается, возможно есть аргументы). Проверить результат запросами:
   - `SELECT n.code, count(*) FROM food_nutrients fn JOIN nutrients n ON n.id=fn.nutrient_id GROUP BY 1` —
     должно быть ~30+ кодов с данными, покрытие сопоставимо со старой базой;
   - выборочно 5 продуктов сверить значения со старой базой;
   - валидация калорий: `kcal_per_100g` против `4P+4C+9F` (+7 г/этанол для
     алкоголя) — у молотого кофе (`tortilgan_*_qahvasi`) явные ошибки (180–200
     ккал при макросах на 400+) — исправь в foods.json реальными значениями
     (~330–400 ккал/100 г у молотого кофе; сверь макросы тоже).
7. FTS-индекс и штучные порции коллеги (`is_piece`-логика в build-скрипте) не
   ломать — прогони его тесты/проверки, если есть.
